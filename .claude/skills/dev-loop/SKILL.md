# Цикл разработки

Цель: изменение работает в игре на телефоне, покрыто тестом, собрано в пакет и записано в документы. Цикл повторяется, пока все проверки шага 4 не зелёные.

## Цикл

1. **Понять.** Найти механику в `docs/gdd/mechanics.md`, код в `scripts/pixel-mine/`. Новая задача: сначала `docs/research/` (решалась ли раньше), находка записывается туда же по шаблону из `docs/research/README.md`. Если задача — новая фича, сначала `/speckit-specify`, потом `/speckit-plan` и `/speckit-tasks`.
2. **Тест.** Изменение правила: сначала проверка в `tests/test-engine.mjs` или `tests/test-campaign.mjs`, она должна упасть. Изменение экрана: описать, что игрок должен увидеть, в `docs/ux/ux-map.md`.
3. **Изменить.** Правило в `model/`, связка с Construct в `game/`, экран в `ui/`, числа в `config.js`. Новое поле профиля получает значение по умолчанию в `model/profile.js`.
4. **Проверить** (скилл `verify-build`):
   - тесты движка и кампании зелёные;
   - эталонный прогон `tests/golden.mjs` совпадает. Не совпал — разобрать почему. Перезаписать `--write`, только если поведение поменялось намеренно, и сказать об этом;
   - проверка типов без новых ошибок.
5. **Показать.** Экран — в браузере на четырёх размерах (`mobile-check`). Заметное изменение — в Preview Construct (`construct-preview`). Спорный для новичка экран — `persona-playtest`.
6. **Записать.** Механика в `docs/gdd/mechanics.md`, экран в `docs/ux/ux-map.md`, ассет в `docs/art-bible/assets.md`, спецификация в `specs/`.

## Готово, когда

- Все проверки шага 4 зелёные, и в выводе это видно, а не предполагается.
- Экран проверен на 375×667, 390×844, 360×800, 768×1024.
- `build/pixel-mine.c3p` собран, `verify-pack` проходит.
- В отчёте пользователю сказано, что не проверено (например, «в Construct не открывал»).

## Ловушки

- Нельзя «чинить» эталонный прогон перезаписью, не поняв расхождение.
- Тексты для игрока идут через скилл `game-copy`.
- Временные скрипты пишутся в файл, а не через heredoc: Git Bash съедает обратные слэши.
